# pixi-skills — Project Context

## What This Project Is

`pixi-skills` is a **provider-agnostic, reproducible skills manager**
for AI coding agents (Claude Code, Cursor, GitHub Copilot, Codex, etc.).

Skills are markdown files — typically `SKILL.md` — that teach AI agents
domain-specific knowledge: how to use an API, how your codebase is
structured, how to run certain tasks. They are to AI agents what
man pages are to humans.

`pixi-skills` manages these skills the same way cargo manages Rust
crates or pixi manages conda packages: with **versioning, lockfiles,
reproducibility, and supply chain security**.

---

## What Problem It Solves

### The skills.sh problem
The incumbent tool (`skills.sh` / `npx skills`) is npm-only and uses
GitHub as a registry with no version pinning. Skills are fetched from
`main` — no lockfile, no version constraint, no reproducibility.
Skills end up vendored into repositories, polluting git history with
markdown diffs you didn't write.

### The pixi-skills solution
- **Lockfile-first**: `skills-lock.toml` pins exact versions and hashes.
  Skills are reproducible across machines, time, and teams.
- **Provider-agnostic**: GitHub repos, conda channels, prefix.dev, PyPI —
  all through the same `SkillRegistry` trait.
- **Conda-native**: skills can be published as conda packages, gaining
  versioning, private channels, and pixi-pack offline bundling for free.
- **Cross-language**: conda = any language. Not npm-only.
- **Enterprise-ready**: private conda channels, signed packages,
  airgapped environments via pixi-pack.

## The Three-Layer Task Model

All automation is unified under `pixi run`. The model has three layers:

```
┌────────────────────────────────────────────┐
│               pixi tasks                   │  ← User entry point
│        orchestration + glue layer          │  ← "pixi run <anything>"
├────────────────┬───────────────────────────┤
│  cargo xtask   │     bun run <script>      │  ← Domain-native automation
│ (Rust concerns)│   (Astro/JS concerns)     │
├────────────────┼───────────────────────────┤
│ Rust toolchain │  Bun + Node runtime       │  ← Both provided by pixi
└────────────────┴───────────────────────────┘
```

**pixi** = what to run and in which environment
**cargo xtask** = how to do Rust codegen, release, workspace lint
**bun scripts** = how to do Astro dev/build/preview/check
**standalone CLIs** = sharp tools (taplo, biome, cargo-deny, convco, nextest)

No shell scripts. No Makefiles. One entry point.

## Key Design Principles

1. **Reproducibility over convenience** — lockfiles everywhere.
   `pixi.lock` pins the toolchain. `skills-lock.toml` pins skills.
   `bun.lock` pins JS deps. Every machine runs identical software.

2. **Provider trait over hardcoded sources** — `SkillRegistry` is a
   trait. New providers (OCI, custom HTTP, local FS) are new crates,
   not forks.

3. **Codegen over drift** — CLI docs, JSON schema, and shell
   completions are all generated from the real Rust source by xtask.
   They cannot drift from the implementation.

4. **pixi as the universal entry point** — contributors only need to
   know `pixi run <tab>`. They do not need to know which layer owns
   which task.

5. **conda-native, not conda-only** — the conda provider is
   first-class, but GitHub compatibility means instant access to the
   existing skills.sh ecosystem on day one.

## Relationship to the Wider Ecosystem

```
pixi-skills
    │
    ├── is a pixi extension (named pixi-skills, invoked as `pixi skills`)
    ├── uses rattler crates internally for conda channel access
    ├── is compatible with pixi-pack (skills bundles can be offline-packed)
    ├── is compatible with skills.sh GitHub repos (provider-github)
    └── publishes skills as noarch conda packages on conda channels
```
